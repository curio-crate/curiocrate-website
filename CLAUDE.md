# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The marketing/donor website for CurioCrate, a STEM nonprofit (501(c)(3), est. 2023) that delivers free hands-on science kits to underserved communities. React SPA with heavy Framer Motion animation, deployed to **Cloudflare Pages** (curiocrate.org) — confirmed 2026-08-04 via the Cloudflare dashboard's Workers & Pages section. (An earlier version of this file incorrectly said Netlify; the `_headers`/`_redirects` config files use that same filename convention because Cloudflare Pages adopted it for Netlify-migration compatibility — don't take the presence of those filenames as evidence of which platform is actually hosting the site. Verify docs like this against reality before trusting them, this one was wrong for a while.)

## Commands

- `npm run dev` — start Vite dev server
- `npm run build` — production build to `dist/`
- `npm run lint` — ESLint
- `npm run preview` — serve the production build locally

No test suite exists in this repo.

## Architecture

**Stack:** React 19 + React Router 7 (`BrowserRouter`) + Vite 8 + Tailwind CSS 4 (via `@tailwindcss/vite`) + Framer Motion. `leaflet`/`react-leaflet` power the chapter map. Three.js/`@react-three/fiber`/`@react-three/drei`/`@react-three/postprocessing` + `gsap` are listed in `package.json` but currently **unused** (as of 2026-08-04) — they powered a cinematic 3D scroll experience on the Kits page that was removed and replaced with a static catalog placeholder (see below). Left in `package.json` rather than uninstalled in case that direction gets revisited; don't assume their presence means something on the live site uses them — check actual imports first.

**Routing** is centralized in `src/App.jsx`: every route is listed there alongside the persistent `CinematicNavbar`, `CinematicFooter`, and `ParticleField` (ambient background) that wrap all pages.

**Legacy vs. active components:** `src/components/` contains both the active set (`CinematicNavbar.jsx`, `CinematicFooter.jsx`, used site-wide) and older unused duplicates left over from a previous design pass (`Navbar.jsx`, `Footer.jsx`, `BoardMembers.jsx`, `Mission.jsx`, the component-level `Gallery.jsx`). None of the legacy ones are imported by `App.jsx` or any page — check `App.jsx` and the relevant page file before assuming a component is live.

**Content is data-driven in two different ways:**
- Simple lists (impact stats, gallery photos, alumni, news, map pin locations) live in `src/data/*.js` and are imported directly by the components that render them.
- Team/board content (`src/pages/Team.jsx`) is hardcoded as arrays (`cabinet`, `directors`, `productOfficers`, `departmentHeads`) at the top of the file, each entry driving a shared `PanelStage` component (hover-to-expand card row). Per-member styling fields (`color`, `glow`, `dark`, `photoHeight`/`photoExpandedHeight`, optional `photoOffsetY`) control a card's theme color and how its cutout photo is sized/positioned — these needed hand-tuning to keep photos level across a row when photo source files have inconsistent framing/aspect ratios, so don't assume a uniform value works for a newly added photo.
- **Our Chapters** (`src/pages/OurChapters.jsx`) is the exception: it live-fetches from a Google Sheet via an Apps Script web app (`VITE_APPS_SCRIPT_URL` in `.env`; the GAS source is in `apps-script/Code.gs`). `src/data/chapters.js` is intentionally an empty array — it's a fallback shape, not real data, and isn't meant to be hand-edited.
  - **Chapters sheet columns (A–R):** A=Email B=PresidentName C=School D=Logo E=State F=City G=PresidentPhoto H=VicePresident I=Treasurer J=Secretary K=SocialMedia L=AuthorizedDirectors M=Type N=Latitude O=Longitude P=Radius Q=Instagram R=PresidentMessage. `getChapters()` in `Code.gs` reads all of A–R and returns them under matching camelCase keys (`type`, `latitude`, `longitude`, `radius`, `instagram`, `presidentMessage`, etc.) — confirmed as of 2026-08-03 that the live sheet has all 18 columns filled in.
  - **Chapter vs. Impact rows:** `Type` (M) distinguishes real student-led high-school chapters (`Type="Chapter"`, or blank) from one-off teaching locations like YMCAs/elementary schools (`Type="Impact"`) — only `Chapter` rows should appear in the "Our Chapters" list/cards (`OurChapters.jsx`); `Impact` rows should show only as map markers, never in the chapter list. `getChapters()` normalizes column M case-insensitively (`/^impact$/i`) into a `type` field — the frontend filters (`c.type !== 'Impact'` in `OurChapters.jsx`, `c.type === 'Impact'` in `Home.jsx`) are case-sensitive string comparisons against that value, so if `getChapters()` ever stops returning `type` (as it did until 2026-08-03 — it silently omitted the field entirely, so every row's `type` was `undefined` and `undefined !== 'Impact'` meant Impact rows always leaked into the chapter list) or the normalization is removed, the bug comes back.
  - **Chapter map markers:** `Home.jsx`'s map prefers real `latitude`/`longitude` from the sheet (N/O) when present, falling back to a static `src/data/chapterLocations.js` lookup by school name for `Chapter`-type rows only — `Impact`-type rows have no such fallback, so an Impact row needs real N/O coordinates in the sheet to ever show up as a map marker. `radius` (P) sizes the impact-area circle in km, defaulting to 12.
  - **Leaflet unmount crash (fixed 2026-08-29):** navigating away from `Home.jsx` while the map's `FitToMarkers` component was mid-animation (its `useMap()`-driven `map.fitBounds()` call, which runs on mount and re-runs whenever its `markers` prop changes) could crash the whole app with `TypeError: Cannot read properties of undefined (reading '_leaflet_pos')` — Leaflet's `transitionend` handler firing after react-leaflet had already torn down the map's DOM panes. Two changes fixed it: (1) the marker arrays feeding `FitToMarkers` are now `useMemo`'d on `chaptersData` in `LeafletMap` (previously recomputed as fresh array literals — including a bare `[...spreadChapters, ...spreadTeaching]` spread inline in JSX — on every unrelated `Home` re-render, which re-triggered `fitBounds`'s pan/zoom animation far more often than intended, meaning far more opportunities to be mid-animation when a visitor navigates away); (2) `FitToMarkers`'s effect cleanup now calls `map.stop()` to cancel any in-flight animation before unmount. **`map.stop()` itself is not safe to call unconditionally** — confirmed live that calling it after react-leaflet has already torn down the map's internal state throws that exact same `_leaflet_pos` error from inside `stop()`'s own `setZoom`/`getCenter`/`_moved` call chain (React does not guarantee this child effect's cleanup runs strictly before `MapContainer`'s own removal effect) — so it's wrapped in `try/catch`, which is required, not just defensive style. Verified via a real rebuild + stress-test loop simulating rapid navigation away from `/` (a stale-bundle false negative during that verification is a good reminder that `vite preview` can serve a browser-cached JS bundle after a rebuild — force a hard reload / fresh tab / cache-busting query param when re-testing after rebuilding, don't trust a `navigate` call alone).
  - **`apps-script/Code.gs` is shared with the Volunteer Portal** (a separate site) — it's the "Curio Crate Volunteer Portal" backend first and foremost (Curriculum/Events/Volunteers/Directors/DirectorRequests, timezone handling, gviz-safe instant columns, form-response sync, etc.), and the marketing site's `get_chapters`/`get_updates` endpoints are a small addition on top. When touching this file for a marketing-site reason, change only what's needed for that fix and leave the portal-related functions untouched — a careless edit here breaks volunteer-portal features for the other site, not just this one. **Always confirm the actual live script content with the user before editing it** — the version previously committed to this repo had drifted significantly from what was really deployed.
  - **After editing `Code.gs` you must redeploy** (Google Sheet → Extensions → Apps Script → Deploy → Manage deployments → pencil icon → Version: New version → Deploy) — saving the file alone does not update the live `/exec` URL that both sites call.

**Asset serving gotcha:** Several asset folders exist twice — once at the repo root (`boardmembers/`, `logos/`, loose image/video files) holding source originals, and once under `public/` (`public/boardmembers/`, `public/images/`, `public/logos/`, etc.) which is what Vite actually serves. Dropping a new file only at the repo root will 404 on the live site — it must also be copied into the matching `public/` subfolder.

**Deploy/caching (Cloudflare Pages):** The site is built and hosted directly on Cloudflare Pages (Cloudflare dashboard → Workers & Pages), connected to this GitHub repo for auto-deploy on push to `main` — there is no separate origin behind a CDN proxy; Cloudflare's edge cache and the Pages hosting are the same platform. `public/_headers` sets `index.html` to `no-cache` and `/assets/*` to `max-age=3600` (see below for why this isn't a long/immutable cache despite Vite content-hashing every JS/CSS filename). `public/_redirects` has the SPA fallback (`/* -> /index.html`) but explicitly carves out `/assets/*` first so missing assets 404 instead of being served the HTML shell.
- **Incident (2026-08-04):** users got "Failed to load module script... MIME type text/html" on a hashed `/assets/*.js` URL, persisting across hard refresh, incognito, disabled extensions, and a different network (cellular vs. home wifi) — that combination rules out anything client-side. Root cause: a request for a newly-deployed hashed asset URL landed in the brief propagation window right after a Cloudflare Pages deploy went live (before that file was fully available everywhere), got back the SPA-fallback HTML with a 200 status, and Cloudflare's edge cached *that* response under the `/assets/*` header rule — which at the time said `immutable, max-age=31536000` — regardless of the fact that the content didn't match what the URL was supposed to be. Once cached, no hard refresh or revalidation could fix it; it required a manual dashboard purge (Caching → Configuration → Purge Everything). **Caution:** testing a *freshly deployed* hashed URL yourself with `curl`/`WebFetch` within the first several seconds of a deploy can trigger this exact same poisoning (happened once, live, while diagnosing this very incident) — wait longer before checking, or be ready to purge again.
- **Fix (2026-08-04):** dropped `/assets/*` from `immutable, max-age=31536000` down to a plain `max-age=3600` (1 hour) in `public/_headers`. This means if the propagation-gap race ever poisons a cached response again, it self-corrects within an hour on its own — no purge, no webhook, no build plugin needed. The tradeoff is losing some of the performance benefit of caching content-hashed assets forever (a repeat visitor may occasionally re-fetch a file that, in principle, never changes) — a reasonable trade for a moderate-traffic nonprofit site given the alternative is a full year of being stuck broken. **Do not put `immutable` or a very long `max-age` back on `/assets/*` without also solving the propagation-race problem some other way** (e.g. a verified, working Cloudflare Pages "purge on deploy" mechanism) — reintroducing it reopens this exact incident.
- Two failure modes produce the same browser error message — diagnose before assuming it's the trivial one: (1) stale `index.html` in the visitor's own cache, fixed by a hard refresh (self-resolves since `index.html` is `no-cache`); (2) the edge-poisoning scenario above, NOT fixed by a hard refresh, and often geographically inconsistent (some regions/PoPs affected, others not) — a `curl`/`WebFetch` check from one location can look completely fine while other users still see it.
- If you ever need to force a brand-new asset URL on demand (e.g. to sidestep a cache issue immediately without waiting out the hour, or to force all clients onto a fresh bundle right away), bump the `window.__CURIOCRATE_BUILD__` marker string in `src/main.jsx` — it exists purely to force a new Vite content hash.
- **Do not assume Netlify.** An earlier version of this file incorrectly said the site was on Netlify, and real work (a `netlify.toml` + Netlify Build Plugin meant to auto-purge Cloudflare's cache after each deploy) was built and shipped against that wrong assumption before it was caught and removed — it would have silently never run, since there was no Netlify build pipeline to invoke it. `public/_headers`/`public/_redirects` are not proof of platform; Cloudflare Pages deliberately supports the same filenames for Netlify-migration compatibility. If deploy/hosting platform ever matters for a task, confirm it (e.g. ask the user to check their Cloudflare dashboard's Workers & Pages section, or check for platform-specific response headers) rather than trusting this file or file-format conventions alone.

**CSS:** `src/index.css` starts with the Google Fonts `@import` followed by `@import "tailwindcss"`. Per the CSS spec, `@import` rules must precede all other rules — reordering these (e.g. putting other CSS before the font import) has previously broken every custom font site-wide, silently.

**Kits page (`src/pages/Kits.jsx`) — funding progress bar, no countdown (as of 2026-08-29):** No real kit products exist yet. The page is currently just a funding progress bar (`src/components/KitProgressBar.jsx`) plus the fixed `InternshipBanner`, sitting directly under the navbar — there is deliberately no hero/countdown above it, see below.
- **A "our first kit is launching in" countdown (`src/components/KitCountdown.jsx`) existed from 2026-08-04 to 2026-08-29, then was deleted outright** at the site owner's explicit request once it became clear `LaunchAt` was never going to be set: rather than keep a static "Launch date coming soon" placeholder (which is what the page correctly showed with `LaunchAt` empty — not a bug, verified live multiple times), the owner asked to remove the countdown from the page entirely. If a future request references a full-screen countdown, `DD:HH:MM:SS` flip digits, `FlipDigit`/`DigitBurst`, `LoadingOrb`, or a `LaunchAt`-driven hero on this page — that's this now-deleted iteration; don't go looking for `KitCountdown.jsx`, and don't assume `Kits.jsx` still fetches/uses `LaunchAt`/`LaunchAtText` (the `kits.defaultIntro`/`comingSoon`/`arrived`/`loading`/`labels` i18n keys were removed along with it too). **Removing it left a large empty stretch of ambient `ParticleField` background between the progress bar and the fixed banner** — flagged to the owner, not fixed unprompted, since it wasn't asked for.
- **The funding progress bar (`src/components/KitProgressBar.jsx`, added 2026-08-29)** is driven by the `get_kit_status` Apps Script action (`getKitStatus()` in `apps-script/Code.gs`, returns the `KitStatus` sheet's rows): a special-cased `ProgressBar` row (`status.progressBarGoal`/`status.progressBarCurrent`) and any number of `Checkpoint` rows (returned as a separate, amount-sorted `checkpoints` array — see the `KITSTATUS SHEET` doc comment in `Code.gs`). Renders nothing if there's no `ProgressBar` row (goal `<= 0`), same "never show fake/misleading data" philosophy the countdown used to follow. **The live deployed Apps Script had drifted from the repo copy** before this feature was added — the repo assumed a `LaunchAtText` (KitStatus column C) feature that was never actually deployed; that assumption was dropped rather than restored when this was built.
  - **Redesigned same day (2026-08-29) into a full-bleed "water tube"** at the site owner's explicit request — no card/container, no CTA button, no trust-badge row, no title/stage copy; just the stat line and a thick, edge-to-edge, full-viewport-width tube styled with 3D glass shading (gradient + inset shadows), an animated SVG ripple tiled across the water's surface (`WAVE_SVG`, scrolls via `background-position`), and checkpoints laid out as a timeline — small dots on the tube with name/amount labels alternating above/below on tick lines, not boxed cards. The percentage badge next to the big dollar figure shows progress toward the **next unreached checkpoint** (`pctToNext`), not the overall goal — falls back to overall-goal percentage once every checkpoint is reached or if none exist. This is deliberate goal-gradient framing (a nearer target reads as a bigger, faster-moving percentage), same psychology rationale as the removed roadmap-card design, just expressed more minimally per what was asked.
  - **A genuinely subtle CSS bug surfaced while building the timeline positioning, worth knowing if this pattern gets reused anywhere:** an absolutely-positioned wrapper element whose *only* children are themselves absolutely positioned collapses to a 0×0 box (no in-flow content to size around) — confirmed live via `getBoundingClientRect()`. Any percentage `left`/`top`/`bottom`/`right` set on a child of that wrapper silently resolves against that zero size and does nothing, while a `transform: translateX(-50%)` on the same child works fine (transform percentages are relative to the *element's own* size, not the parent's) — so centering can look correct by accident while edge-position clamping or "float above/below with a gap" spacing silently no-ops. Symptom here was a checkpoint at exactly 100% rendering its label centered on the true, un-clamped edge (clipped ~32px off-screen) and a connecting tick line running visibly into the tube's body instead of stopping cleanly at its edge. Fix: give positioned children real percentage anchoring by making them direct siblings against an ancestor that actually has real dimensions (here, `.kpb-timeline`, sized via `inset: 0` to match the tube) rather than nesting them under a shared zero-size "marker" wrapper.
  - **Entrance-animation bug (fixed 2026-08-29, same day):** the card originally animated in via Framer Motion's `useInView` (`once: true`, IntersectionObserver-backed), replaying on every fresh page load. Confirmed live on production this could leave the entire section — card opacity, bar fill, count-up number, checkpoint fade-ins, ALL of it, since every one of them was gated on that same single `inView` boolean with no fallback — permanently invisible (`opacity: 0` forever, verified via `getComputedStyle`, real fetched data present in the DOM the whole time). Root cause: if the browser never fires that IntersectionObserver callback for the element (reproducible reliably in an automated/backgrounded tab, per the rAF-throttling gotcha below the Kits countdown section used to warn about — but per a live "why don't I see anything" report, apparently reachable by real visitors too, e.g. a tab that loads in the background), `animate={inView ? {...} : {}}` never has anything to animate to, so it just sits at `initial`. **Fixed by dropping `useInView` entirely** — `ready` is now a plain `useState(false)` flipped by an unconditional `useEffect(() => setReady(true), [])`, which isn't tied to intersection/visibility at all. Made sense to drop the "replay on scroll into view" behavior too, not just work around it: this section sits right below the navbar now (no hero above it since the countdown was removed the same day), so it's already essentially always in view on load — animate-on-mount achieves the same "plays every time you load the page" intent with one less moving part. **If a future animated section on this site uses `useInView`/`whileInView` and reports of "I don't see anything" come in, suspect this same class of bug first** — check `getComputedStyle(...).opacity` on the supposedly-missing element before assuming a data/fetch problem.
- **`Kits.jsx` tracks fetch-in-flight as a `loading` boolean** so the fixed `InternshipBanner` doesn't pop in before the progress bar's data is ready. Apps Script backends are genuinely slow to respond — **measured against this spreadsheet: 20-45s on a cold hit, ~2-3s once warm**, and occasionally slow enough (44s observed once) to exceed even the 40s client-side timeout below — significantly worse than "a second or two." The fetch is wrapped in an `AbortController` with a 40s timeout (added 2026-08-29 after a cold-start run left the page stuck waiting indefinitely, which also hid the progress bar since it depends on the same request) so a slow-enough or genuinely stalled response still resolves to the "no data yet" state instead of hanging forever.
- **`getKitStatus()` in `apps-script/Code.gs` caches its finished JSON response via `CacheService.getScriptCache()` for 60s** (added 2026-08-29, same day, after the 20-45s cold latency above turned out to be `SpreadsheetApp`/sheet access itself being slow against this particular multi-sheet workbook, not something fixable in this function's own logic). Only the first request after a cache expiry pays the cold-open cost; every request within the 60s window after that returns near-instantly straight from cache, without touching the spreadsheet at all. 60s was chosen so an admin editing the KitStatus sheet (ProgressBar, Checkpoint rows) still sees it reflected on the live site within a minute, with no redeploy needed — this sheet is read live, unlike code changes. `getChapters()`/the `get_updates` handler read the same slow-to-open spreadsheet and don't have this caching — if they start showing the same "slow/looks stuck" symptom, the same fix likely applies there too, but hasn't been added since it wasn't asked for and touching shared Apps Script code beyond what's needed is deliberately avoided (this file also backs the Volunteer Portal).
- **This page has had four iterations**, in order: an earlier cinematic 3D scroll-driven "unboxing" experience (GSAP `ScrollTrigger` + React Three Fiber, deleted alongside `src/components/kitExperience/`); a brief static "coming soon" catalog placeholder that stood in for one day; the `LaunchAt` countdown described above (2026-08-04 to 2026-08-29); and the current progress-bar-only page. If a future request references "the 3D kit experience," "the box that opens," camera chapters, `TOTAL_VH`, HUD callouts, or a catalog grid of placeholder kit categories — those are earlier, now-deleted iterations too; don't assume any of them still exist, and don't go looking for `kitExperience/` files that are gone.
- **Testing note:** this page's entrance/flip animations rely on `requestAnimationFrame`, which Chrome throttles heavily in automated/backgrounded browser tabs (confirmed while building this — a tab driven via browser automation sat with `.page`'s opacity frozen near 0 indefinitely, looking like a rendering bug, until forced visible with an injected `!important` CSS rule). Separately, `npm run dev`'s React `<StrictMode>` double-invokes effects, which combined with that same rAF throttling froze `FlipDigit`'s `AnimatePresence` mid-transition on first load, showing a ghosted double-exposure of two overlapping digits — this did **not** reproduce against a real production build (`npm run build && npm run preview`), confirming it was a dev-mode-only artifact, not a real bug. **If a countdown/animation on this page ever "looks broken" only when checked via automated/dev-mode tooling, check against a `preview` build in a normal focused tab before concluding the code is wrong.**

**Internationalization (English/Spanish, added 2026-08-04):** `src/i18n/` — `LanguageContext.jsx` (provider + the `t()` translation function), `useLanguage.js` (the hook — deliberately split into its own file, not exported alongside the provider component, because mixing a component export and a hook export in one file breaks React Fast Refresh / trips `react-hooks/only-export-components`), `context.js` (the raw React context object, also split out for the same reason).
- **Translation strings live in `src/i18n/translations/pages/*.js`, one file per page/concern, NOT one shared dictionary.** Each file exports `en` and `es` objects, each with its own unique top-level namespace key (e.g. `common.js` → `common`/`nav`/`footer`; `home.js` → `home`; `team.js` → `team`; `initiatives.js` → `kitDevelopment` + `handsOnTeaching`; `chaptersAndGallery.js` → `chapters` + `gallery`; `misc.js` → `newsletterPage` + `contact` + `kits`). `LanguageContext.jsx` auto-discovers and merges all of them at build time via `import.meta.glob('./translations/pages/*.js', { eager: true })` — **adding a new page's translations means creating a new file here, never editing an existing one.** This was deliberate: several pages got translated in parallel by separate agents, and a single shared dictionary file would have been a guaranteed edit-conflict point; per-file-per-page with auto-merge made that safe. Keep this pattern for any future page/section that needs translating, even if it's just you (not parallel agents) doing it — it's still the established convention here.
- **Usage pattern**: `const { t, lang, setLang } = useLanguage()`, then `{t('home.hero.title')}`. Missing keys fall back to the English dictionary, then to the raw key string itself, so a typo'd key never crashes — it just silently shows English or an ugly key string (grep the rendered page for a literal `.` in unexpected places if something looks untranslated). For **data-driven/array content** (e.g. Team.jsx's per-person `role`/`bio`, keyed by each member's own `id`), `t()` takes an optional second argument as an explicit fallback: `t(\`team.cabinet.${m.id}.bio\`, m.bio)` — this shows the correct original English text if that specific key was never translated, instead of a broken path string.
- **Auto-detection**: defaults to Spanish if the browser's `navigator.languages` includes any `es*` locale (the standard client-side, privacy-respecting proxy for "visitor is likely Spanish-speaking" — deliberately NOT IP-based geolocation, which would need a paid/keyed third-party API and raises privacy questions this approach avoids). An explicit manual choice via the `LanguageSwitcher` component (in both the desktop nav and mobile menu overlay) is persisted to `localStorage` (`curiocrate_lang`) and wins over auto-detection on future visits.
- **Data fetched live from Google Sheets is intentionally never translated** (chapter info in `OurChapters.jsx`, news/updates in `Home.jsx`/`Newsletter.jsx`, the `KitStatus` sheet's `LaunchAtText` admin caption in `KitCountdown.jsx`) — only the static page chrome around it goes through `t()`. Translating live admin-authored content would require a translation pipeline on the Apps Script side that doesn't exist; don't assume it's just an oversight if you find fetched data rendered without `t()`.
- **Testing tip for narrow viewports**: `resize_window` (browser automation) does NOT actually change a tab's real viewport/`window.innerWidth` in this environment — confirmed while testing mobile layout, it silently no-ops. What does work: inject a **same-origin** `<iframe>` sized to the target viewport (e.g. `width:375px` via `iframe.style.cssText`) pointing at the same dev/preview server URL, since an iframe gets its own genuine viewport that real `@media` queries and `window.innerWidth`-based JS (like the `useMobile` hook) correctly see. Must be same-origin (same port) as the outer tab or `iframe.contentDocument` access is blocked by CORS. Also: a page's entrance-fade animation may be mid-transition when you screenshot (especially combined with the rAF-throttling issue noted above) — inject `<style>.page, .page * { opacity: 1 !important; filter: none !important; }</style>` into the iframe's own document first to force the resting state before screenshotting.

**Mobile responsiveness pass (2026-08-04):** several pages had no responsive CSS at all, or had it but it silently didn't apply — check for this pattern (a `className` referenced only by a `@media` rule that's never actually attached to any element, or vice versa) before assuming a page is fully responsive just because *some* `@media` blocks exist in the file. Fixed: `CinematicNavbar.jsx`'s fully-transparent "atTop" background collided visually with the hero heading on mobile (now forces a legible gradient+blur backdrop under 768px regardless of scroll position); `Home.jsx`'s alumni watermark logos overflowed their card (capped on mobile) and the "Our Reach" stats strip's own mobile CSS was dead code from a className mismatch (now wired up); `KitDevelopment.jsx`'s tab bar and `HandsOnTeaching.jsx`'s two-column grids had zero mobile handling at all (both now stack/reflow under 640-768px); `Newsletter.jsx`'s card images used a CSS-grid-stretched `height:100%` that had no definite height to resolve against once the grid collapsed to one column on mobile (now gets an explicit height). `ParticleField.jsx` (global ambient background, every page) skips its O(n²) connecting-line effect and uses fewer particles under 768px — real cost on low-power mobile hardware, a likely contributor to "site feels slow on phone" reports.
